A website speed quote depends on what is slow and who will fix it. An audit can identify a slow product page or checkout interaction. An implementation quote should say which fixes are included, how they will be tested and who owns changes outside that scope.

## 1. Scope to compare in a speed optimization quote

Start by separating diagnosis from implementation. A WordPress brochure site may need image and cache changes on a few templates. A store may require cart and checkout tests as well. A custom app can involve application code, backend work and a release coordinated with the team that owns the repository.

| Scope | What to ask for | What can expand the work |
| --- | --- | --- |
| Audit only | Baseline, affected pages, likely causes and an ordered fix list | Testing more templates or reproducing an intermittent issue |
| WordPress site | Included templates, image changes, cache rules and a staging check | Theme overrides, plugins or hosting restrictions |
| Online store | Product, cart and checkout tests with cache exclusions | Dynamic pricing, payment scripts and integrations |
| Custom app | Affected routes, code changes and a release plan | Backend dependencies, third-party code and deployment approvals |

Ask the provider to name the pages in the quote. A fix on the home page may leave product and checkout templates untouched. Agree on who can change the CDN and hosting configuration, who reviews the patch, and who reruns the tests after release. A quote that leaves those roles open is hard to compare.

Ask each vendor to show how a proposed fix relates to a reported issue. If the hero image dominates LCP, find out whether the quote covers the image, its request priority, and the template that renders it. If checkout is slow after a click, ask for a trace of the interaction. A change to cache settings may have little effect on that delay.

Request the same exclusions from each provider. Hosting migration, an analytics rebuild and replacing a payment plugin are separate decisions when they are outside the agreed scope. Clarify whether the provider will make recommendations for those items or implement them. That distinction can explain a difference in quotes without any difference in the quality of the work.

## 2. What Moves Your Quote Up or Down

Your final quote moves with four things: how much legacy bloat the site already carries, how complex the database and checkout logic are, whether the current host can serve cached content properly, and how many third-party scripts are embedded in templates. Cleaning up before optimizing usually costs less than optimizing around the mess.

- **Legacy plugin and theme weight.** A site carrying years of abandoned plugins pays for their removal first; dead code still ships to visitors until someone deletes it.
- **Database size and query health.** Large catalogues, unbounded postmeta growth, and slow queries push work into the e-commerce or custom tier regardless of the front end.
- **Hosting tier.** A server that cannot serve cached pages properly caps what any frontend optimization can achieve, and the fix is a migration, not a plugin.
- **Third-party embeds.** Chat widgets, A/B tools, and review widgets load on every page and are rarely inside your provider's default scope.
- **Scope of the redesign.** If templates must be rebuilt to remove unsized images and blocking styles, you are buying front-end work as well as tuning.
- Ask whether the audit is priced separately. The diagnosis may narrow the implementation work to a few templates and give you a baseline for testing.

## 3. Compare Core Web Vitals with a consistent baseline

The three Core Web Vitals measure different parts of the visit. LCP measures when the largest visible content element renders, INP measures responsiveness to user interactions, and CLS measures unexpected movement on the page. Google evaluates the 75th percentile of visits and recommends reviewing mobile and desktop results separately.

Good thresholds are LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1. These are experience benchmarks. When field data is sparse, repeat a controlled lab test and label the result as lab data. A lab run can help locate a problem without establishing that real visitors have reached the threshold. [Google’s Core Web Vitals thresholds](https://web.dev/articles/vitals).

Give the provider a list of representative pages and actions. For a shop that might mean opening a product page, choosing an option and adding it to a cart. Ask for the test environment and a way to reproduce each result. Save the baseline with the quote so you can check the same pages after the work ships.

## 4. Technical Scope of Enterprise Speed Tuning

Professional speed work covers four layers at once: asset modernization, JavaScript and CSS optimization, database and backend refinement, and network edge delivery. A caching plugin touches part of one layer only, which is why plugin-only tuning stalls well short of the thresholds Google scores you on:

```
┌─────────────────────────────────────────────────────────┐
│              The 4 Pillars of Real Speed Tuning         │
├─────────────────────────┬───────────────────────────────┤
│ 1. Asset Modernization  │ Lossless WebP/AVIF compression│
│                         │ and responsive image srcset   │
├─────────────────────────┼───────────────────────────────┤
│ 2. JavaScript & CSS     │ Code-splitting, critical CSS  │
│    Optimization         │ inlining, deferring 3rd party │
├─────────────────────────┼───────────────────────────────┤
│ 3. Database & Backend   │ Query indexing, transient     │
│    Refinement           │ cleanup, reducing TTFB < 200ms│
├─────────────────────────┼───────────────────────────────┤
│ 4. Network Edge Delivery│ HTTP/3, Brotli compression,   │
│                         │ Cloudflare Edge rules         │
└─────────────────────────┴───────────────────────────────┘
```

**1. Asset modernization.** Convert originals to modern formats at the CDN or build step, serve responsive sizes per breakpoint, reserve dimensions so nothing reflows, and let the largest viewport element load with priority while the rest waits.

**2. JavaScript and CSS optimization.** Split bundles by route, inline the styles needed for first paint, drop dead rules, and defer everything third-party until after the page is usable. Most recurring regressions enter through tag managers here.

**3. Database and backend refinement.** Clean transient and autoloaded data, index the queries that repeat, and remove slow plugins from the request path. This is the tier plugin-only fixes never reach, and it is why dynamic stores price higher.

**4. Network edge delivery.** Serve over HTTP/3 with Brotli compression, set explicit cache rules at the edge, and route visitors to the nearest point of presence so distance stops dominating the response time.

## 5. Estimate the return from your own data

Estimate payback with your own baseline and a stated assumption about how conversions might change. Start with orders or qualified leads from the affected pages, then consider the contribution margin and implementation cost. Run a scenario where conversions stay flat alongside any upside scenario so the decision does not depend on a forecast.

After launch, compare equivalent reporting periods and note changes in campaign mix, pricing or stock. Track conversions separately from the performance metrics. If page responsiveness improves while orders stay flat, report both outcomes. Extra revenue alone is insufficient to calculate payback because order costs and the price of the work also matter.

Include enough detail for a colleague to repeat the comparison. Save the URLs, devices, measurement tool and release date. If the project includes checkout changes, count completed orders and verify that tracking fires at the correct step. If it is a lead generation site, agree on what qualifies as a useful inquiry before comparing results.

## 6. When Do You Need a Professional Speed Optimization?

When deciding who should fix the problem, use the affected customer journey as your starting point. A repeatable delay at checkout or a slow product template with meaningful traffic warrants investigation. Trace the bottleneck before paying for changes across the entire site, and agree on the checks you will repeat afterwards.

1. Check Search Console for affected URL groups when field data is available.
2. Reproduce the problem under documented lab settings.
3. Ask users which action feels slow and when it happens.
4. Check server metrics when the issue coincides with traffic peaks.

A test plan can also reveal work that should wait. Suppose a product page looks slow in a cold lab run but the main delay that shoppers report occurs after selecting a variation. Ask the provider to record both problems and price the interaction fix separately. Test the same selection with representative product data before and after the release. If the test confirms the interaction improves, use that result to decide whether the image work is still worth including. Repeat the check after any later change to the product template, and record what changed so you can distinguish a regression from a different test environment.

## 7. How to Compare Speed Optimization Quotes

Compare quotes on scope, not headline price. Ask each provider for the specific fixes included, the baseline they will measure against, what falls outside the engagement, and what happens to the gains after the site publishes new content. A cheaper quote that omits database work or field-data verification is not cheaper.

1. **Ask for the baseline.** A provider who has not measured your pages before quoting is guessing at the tier you need.
2. **Require a line-item scope.** It should map onto the four pillars: assets, scripts, database, edge. Missing pillars mean missing work.
3. **Clarify what is excluded.** Redesigns, plugin development, and hosting migrations are the three exclusions that turn a fixed quote into a change order.
4. **Confirm how results are verified.** Gains should be re-measured on the same pages, in field data, after the work ships — not declared from a single lab screenshot.
5. **Ask who owns regressions.** Publishing new content reintroduces weight; find out whether a follow-up pass inside the engagement window is included.
6. **Check the access you must grant.** Server, CDN, and tag manager access are prerequisites. A quote that assumes none of them will stall on day one.
7. **Price the ongoing cost.** Quarterly audits are how gains hold; ask for that rate up front rather than renegotiating after the first decay.

## 8. Conclusion

Budget for speed the way you budget for any work that compounds: pay for the fixes that remove the bottleneck, hold the line with clean publishing habits, and re-measure on a schedule. For most sites that means one focused engagement followed by lightweight quarterly audits, not a permanent retainer.
